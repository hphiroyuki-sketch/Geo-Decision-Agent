# 製品化に向けた実装計画（v3.0要件対応）

作成: 2026-09-02 / 対象: Geo Decision Agent v3.0 要件定義書

この文書は「先に計画を立て、論理を検証してから実装する」ための作業計画である。
実装の進行に合わせて更新する。

---

## 0. 誰のための製品か（ペルソナと課題）

実装判断の基準をここに固定する。UIの迷いはすべてこの3人に戻って解く。

### P1. 事業部の計画担当者（35歳・電力会社の再エネ開発部／課題の当事者）

- **やること**: 候補地を3つに絞り、社内会議に「なぜここか」を説明する。
- **困っていること**: 生物多様性の専門家ではない。「配慮しました」と言える根拠がない。
  外部コンサルに出すと数百万円・数か月かかる。社内の環境部から差し戻される理由が読めない。
- **この製品に求めるもの**: 会議で使える1枚。**専門用語が分からなくても意味が取れること**。
  数字の横に「これは良いのか悪いのか」が書いてあること。
- **UIへの含意**: 用語には必ずその場に説明を置く。数値は必ず判定（良好／注意／要対応）とセットで出す。
  空の画面には必ず「次に何をすればよいか」を書く。

### P2. サステナビリティ推進部の担当者（42歳・開示実務）

- **やること**: TNFD/SSBJの開示文書を年1回作る。事業部から情報を集める。
- **困っていること**: 事業部の判断根拠が残っていない。「衛星で見た」と言われても検証できない。
  開示のLEAP各段階に、社内のどの資料が対応するのか分からない。
- **この製品に求めるもの**: **LEAPの段階別にそのまま転記できる出力**。データの時点・出所・確認者が残ること。
- **UIへの含意**: 根拠ステータス（実データ／推定／現地確認済み）を常時表示。監査証跡を消さない。

### P3. 決裁者（55歳・役員）

- **やること**: 投資判断。5分で読む。
- **困っていること**: 詳細は読まない。しかし判断を誤ると差し戻し・訴訟・レピュテーション毀損になる。
- **この製品に求めるもの**: **結論・リスク・対応状況の3つだけ**。根拠へは必要なときだけ降りる。
- **UIへの含意**: ダッシュボードは結論ファースト。大きな数字と色。詳細は折りたたむ。

## 1. 実装順序と根拠

先に土台（データが取れること）、次に意味づけ（読めること）、最後に成果物（出せること）。
この順序でないと、後段が空の器になる。

| 段階 | 内容 | なぜこの順か |
|---|---|---|
| A（完了） | メッシュ不具合修正・日本語入力・音声入力 | 動かない機能の上に積み増ししない |
| B | 3D地形表示＋メッシュ立体化 | 既にメッシュがある今が最も安く実装できる |
| C | FR-022 衛星指標（NDVI/NDRE/NDMI/NBR） | 後段のレポート・監視の材料。先に無いと空欄になる |
| D | FR-053 TNFD LEAP出力＋FR-034 報告書生成 | C の指標が揃って初めて中身のある開示になる |
| E | FR-060 通知・しきい値 | 監視対象（C）と判断（D）が確定してから鳴らす |
| F | V-01〜V-12 画面完成＋ホスピタリティ改善 | 全機能が出揃ってから導線とUIを整える |
| G | 受入確認（合格判定） | 納品可否の最終判断 |

## 2. 各段階の設計と論理チェック

### B. 3D地形表示

- **やること**: 標高タイル（AWS Terrarium、キー不要）を地形として読み込み、傾き・回転操作を追加。
  メッシュを地形に貼り付け、任意で「類似度の高さ＝柱の高さ」として立体化する。
- **論理チェック**:
  - 地形タイルは z15 までしか無い → メッシュの z17〜18 では地形が粗くなるが、
    起伏の把握という目的には足りる。**過度な期待をさせない表記を添える**。
  - 立体化は「高さ＝何か」を凡例で必ず示す。示さない立体表現は誤読を生む。
  - モバイルで3Dは重い → 既定はオフ、明示的に切り替える。

### C. 衛星指標（FR-022）

- **やること**: Sentinel-2 から NDVI/NDRE/NDMI/NBR を Earth Engine で算出し、
  メッシュのセルと候補地に付与する。雲は QA バンドでマスクし、期間中央値で合成する。
- **論理チェック**:
  - エンベディングと同じ「1点1リクエスト」方式では通信回数が倍増する
    → **4指標を1回の呼び出しでまとめて返す**式を組む（1セル1リクエストを維持）。
  - 雲処理をしないと季節・天候の差が「変化」に化ける → 合成必須。
  - 指標は季節で大きく動く → 前年同期と比較し、単月比較はしない。

### D. TNFD LEAP出力（FR-053）＋報告書（FR-034）

- **やること**: プロジェクトの実データから Locate / Evaluate / Assess / Prepare の4章を生成。
  役員向け・技術者向け・監査向け・TNFD向けの4形式で出し分ける。
- **論理チェック**:
  - **データが無い項目を埋めてはならない**。空欄は「未取得」と明記し、取得手段を併記する。
  - LEAPは開示の枠組みであり、AIが「開示内容を決める」ものではない
    → 生成物は必ず「案」であり、確認者の承認欄を持つ。

### E. 通知（FR-060）

- **やること**: しきい値超過・レビュー依頼・データ更新を通知として記録し、未読管理する。
- **論理チェック**:
  - 通知が多すぎると読まれない → 既定のしきい値は保守的に。重要度を必ず付ける。
  - 通知は「誰が何をすべきか」まで書く。事象だけの通知は無視される。

### F. 画面完成とホスピタリティ

- V-01〜V-12 の各画面を、既存データで意味を持つ形に実装する。
- **論理チェック**: 実データの裏付けがない画面（設備台帳など）は、
  **架空の数字で埋めず**、必要なデータと登録手段を画面上で案内する。

### G. 受入確認

- 全画面を初見の顧客として通し、要件番号との対応表を作り、
  合格/不合格を明記する。未達があれば隠さず書く。

## 3. 守る原則（実装中に迷ったらここに戻る）

1. **追跡できない数字を出さない。** 画面の数値は必ずどの行から来たか言えること。
2. **推定と実測を必ず区別する。** 根拠ステータスを省略しない。
3. **空欄は空欄と書く。** 埋めるための創作をしない。
4. **専門用語はその場で説明する。** 別画面のヘルプに逃がさない。
5. **警告は手遅れになる前に出す。** 数分かかる処理は、始める前に条件の妥当性を検査する。
