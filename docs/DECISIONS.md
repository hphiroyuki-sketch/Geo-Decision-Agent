# 設計判断の記録（ADR）

**「なぜこうなっているのか」が最も再発見に時間のかかる情報。**
コードを読めば「何をしているか」は分かるが、「なぜそうしないといけなかったか」は分からない。
ここは変更するときに読む章であり、**同じ罠を踏み直さないための記録**。

各項目は「決定 / 理由 / 代償 / 変えるなら」で書いてある。

---

## ADR-001 パスワードハッシュを PBKDF2 10,000反復にした

**決定**: PBKDF2-SHA256、反復10,000回（`worker/src/lib/crypto.ts`）。

**理由**: Workers ランタイムに bcrypt / scrypt のネイティブモジュールが無く、WebCrypto の
PBKDF2 が唯一の現実解。**そして反復回数を一般的な推奨値にすると Workers 無料プランの
CPU 10ms を超えて register/login が 500 を返す**（実際に起きた）。

**代償**: 10,000反復は現代の推奨（OWASP は600,000回）より弱い。

**変えるなら**: 有料プランへの移行時に反復回数を上げる。既存ユーザーは
ログイン時に再ハッシュする移行を書く必要がある。

---

## ADR-002 メッシュのサンプリングを16件バッチにした

**決定**: `SAMPLE_BATCH = 16`。フロントが `remaining === 0` まで繰り返し呼ぶ。

**理由**: Workers 無料プランは **1リクエストあたり50サブリクエスト**。変化検知ONだと
1マスにつき Earth Engine を2回（今年＋前年）呼ぶので、16×2=32。安全な範囲に収まる。

**代償**: 400マスなら25往復。UIに進捗表示が必須になる。

**変えるなら**: 有料プランでは1000サブリクエストまで上げられるので、バッチを大きくできる。
その場合 `SAMPLE_BATCH` の1箇所だけ変えれば足りる。

## ADR-003 自己診断の結果を1件ずつ即座にD1へ書く

**決定**: `scheduled.ts` の `record()` は各チェック直後に単独INSERTする。まとめ書きしない。

**理由**: cron 実行にも CPU 10ms が適用される。**まとめて最後に書くと、途中で isolate が
殺されたときに全部消え、「cronが動かなかった」のか「途中で落ちた」のか区別できない。**

**関連**: 同じ理由で `index.ts` は**最初に `cron_heartbeat` を書く**。
これが無いと「cronトリガーが発火していない」と「発火したが全滅した」が見分けられない。

---

## ADR-004 EEアルゴリズム一覧を cron から外した

**決定**: `ee_algorithms` チェックは cron では走らせず、管理画面からの明示操作のときだけ実行する。

**理由**: EE の全アルゴリズム（約1000件）の一覧は約1MBのJSONで、パースだけで CPU 予算を超える。

---

## ADR-005 ハザードタイルのPNGをデコードしない

**決定**: HTTPステータスだけで「該当区域の有無」を判定する。ピクセルを読まない。

**理由**: PNG 1ピクセルを読むには全体の inflate と unfilter が必要で、CPU 10ms に収まらない。
**そして不要**：国土地理院の配信はデータの無い場所で **404** を返すので、
存在の有無はステータスだけで答えられる。

**代償**: 粒度がタイル単位（z16 ≒ 600m四方）になる。
**そのため帳票は「この約600m四方の範囲内に指定区域がある」と書き、
「この地点が区域内にある」とは書かない。** 実際に計算した範囲の数値もそのまま印字する。

**変えるなら**: 点判定が必要なら国土数値情報のベクタデータを取り込むこと。
タイルのピクセル読みでは解決しない。

---

## ADR-006 自己診断に「負例」を必ず入れる

**決定**: `gsi_hazard` チェックは正例（東京都心 z16/58205/25807）と
負例（富士山頂 z16/58022/25882）の**両方**を叩き、**区別できなければ失敗させる**。

**理由**: **これが本システムで最も重要な検証の考え方。**
水リスク判定は「該当地で200・非該当地で404」に全面依存する。
正例しか確認していなければ、*どこでも200を返すサービス*でも診断は緑になり、
**全拠点が「該当あり」と企業向け文書に印字される。**

> **判別できないチェックは、チェックが無いより危険。**
> その結果は事実として引用されるから。

**適用範囲**: 新しい外部データ源を足すときは、必ず「該当する場所」と「該当しない場所」の
両方で確かめること。片方だけの確認は確認ではない。

---

## ADR-007 型を Worker と フロントで二重に持つ

**決定**: `worker/src/lib/leap.ts` と `frontend/src/lib/leapTypes.ts` に同じ型を別々に置く。

**理由**: Worker は `@cloudflare/workers-types`、フロントは DOM 型で tsconfig が分かれている。
共有パッケージを作るほどの規模ではないと判断した。

**代償**: **片方だけ変えても型検査は通る。** 実行時に壊れる。

**変えるなら**: `shared/` ワークスペースを切って両方から参照する。規模が増えたらやるべき。

---

## ADR-008 「混雑」と「失敗」を区別する

**決定**: 外部データ源の応答を、こちら側の事情か提供側の事情かで分類する。
`isProviderSideStatus()` / `isProviderSideError()`（`publicData.ts`）。

| 条件 | 分類 |
|---|---|
| HTTP 429 / 5xx / タイムアウト | **提供側**（busy） |
| 429以外の4xx / DNSエラー / パースエラー | **こちら側**（failed） |

**理由**: Overpass は送信元IP単位でレート制限をかけ、Cloudflare Workers は共有IPから外へ出る。
つまり 429 は**構造的に発生する通常状態**であり、我々の不具合ではない。
それを「取得失敗」と印字すると、企業に渡す文書で製品が壊れて見える。

**同じ関数をライブ取得と定時診断の両方で使うのが要点。**
別々の条件で書いたら実際に食い違った（本番の 521 で表面化した）。

**定時診断も、全ミラーが提供側事情なら緑にする。**
毎日赤い行が出る管理画面は、担当者が読まなくなる。**それが赤い行より高くつく。**

**逆に、429以外の4xx は意図的に赤のまま残す。** WAFがUser-Agentを弾き始めた等の
本物の退行を検知したいので、そこまで緑にしてはいけない。

## ADR-009 デモ記録とピンを「カラム」で区別する

**決定**: `field_records.demo`（0/1）と `field_records.source`（`field` / `pin`）を
スキーマのカラムとして持つ。命名規則やタグ文字列にしない。

**理由**:
- **デモ行が「現地確認済み」として通れば、立地判断の根拠を偽ることになる。**
- **衛星画像上でクリックしたピンは、そこに立って撮った写真と同じ証拠ではない。**

カラムにしてあるので、証拠を数える・ラベルを出すすべての箇所が両者を区別できる。
文字列接頭辞にしていたら、どこか1箇所で必ず取り違える。

**背景**: どちらも必要に迫られて足した。
デモ記録が無いと、現地調査を1度もしていない人は製品が動くところを見られない。
ピンが無いと、現地記録が対象地から400km離れている状況（実際に起きた）で解析が無意味になる。

## ADR-010 LLMに数値を作文させない

**決定**: Claude はツール `analyze_site_candidates` を呼ぶだけ。数値は決定的なエンジンが出す。
システムプロンプトにも「数値を自分で創作してはならない」と明記。

**理由**: 出力が企業に渡る文書である以上、数値の出所を説明できなければならない。
LLMが生成した数値は出所を説明できない。

**関連**: ホップ上限は3。無限ループとコスト暴走の両方を防ぐ。

---

## ADR-011 取得失敗を「事実」として保存する

**決定**: `public_data_cache.status` に `ok / failed / busy / empty` を保存し、
失敗キャッシュの寿命は1時間、成功は30日。

**理由**: **到達できなかった源を黙って落とした帳票は「そこには何も無い」と読める。
真実の逆になる。** 企業向け文書ではこれが最悪の失敗。

「判定不可」は「該当しない」ではない、という区別が帳票の凡例に明記してある。

---

## ADR-012 デプロイを GitHub Actions のみにした

**決定**: `npm run deploy`（ローカル直接デプロイ）は残してあるが、実質すべて CI 経由。

**理由**: 開発サンドボックスから `api.cloudflare.com` に到達できない。

**関連**: 同じ理由で外部API疎通は本番の自己診断でしか確認できず、
それが ADR-003 / ADR-006 の設計を生んでいる。

## ADR-013 MapLibre の `isStyleLoaded()` を使わない

**決定**: レイヤー更新の待ち合わせは `isStyleLoaded()` ではなく、
**目的のレイヤーが addressable になるまでポーリング**する（`MapView.tsx` の `whenStyleReady`）。

**理由**: **`isStyleLoaded()` は「全ソースキャッシュが落ち着いた」ときにしか true にならない。**
この地図は10個のラスターソースを持つ。**1つでも決着しないソースがあると述語は永久に false のまま**で、
その後の処理が一切実行されない。これが「衛星画像もメッシュも表示されない」不具合の根本原因だった。

```ts
if (!map.getLayer("streets")) { timer = setTimeout(attempt, 100); return; }
```

**適用範囲**: MapLibre で「読み込み完了」を待つコードを書くときは、
**本当に必要な条件（そのレイヤーが操作可能か）を直接聞くこと。** 総体的な準備完了フラグに頼らない。

## ADR-014 メッシュのサンプリングは失敗しても必ず analyze する

**決定**: バッチ失敗は3回まで指数バックオフで再試行。
それでも駄目なら残りを諦め、**`finally` で必ず `analyze` を呼ぶ**。加えて「続きから再開」ボタンを置く。

**理由**: 初期実装では1バッチの失敗でループ全体が中断し、
**「64/400 で止まり、ホットスポット0件」** という、成功にも失敗にも見えない状態になった。
部分的な結果でも解析すれば意味があるし、ユーザーは何が起きたか分かる。

## ADR-015 単価表を静的テーブルで持つ

**決定**: `lib/pricing.ts` にモデル別の百万トークン単価をハードコード。外部から取得しない。

**理由**: 価格改定は再デプロイで追随できる頻度でしか起きない。
外部依存を1つ増やす価値がない。

**注意**: **新しいモデルを `settings.claude_model` に設定するときは、
この表にも追加すること。** 表に無いモデルは `claude-sonnet-5` の単価で計算され、
予算判定がずれる。
