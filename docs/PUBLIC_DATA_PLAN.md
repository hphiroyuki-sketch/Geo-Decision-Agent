# 公的データ接続 実装計画

目的：TNFDの「感度の高い地域」5基準のうち、**判定不可としていた3基準**を実データで判定できるようにする。

---

## 1. 調査結果：公開データは実在するか

| 求めるもの | データ源 | 提供形態 | 認証 | 判定 |
|---|---|---|---|---|
| 生物多様性上重要な地域 | **GBIF Occurrence API**（`api.gbif.org/v1`） | REST/JSON。`geoDistance=lat,lng,3km` で半径検索。`facet=iucnRedListCategory` でIUCNカテゴリ別集計 | **不要** | **接続可** |
| 保護区域の近接 | **OpenStreetMap Overpass API**（`overpass-api.de`） | REST/JSON。`boundary=national_park` / `boundary=protected_area` / `leisure=nature_reserve` を半径検索 | **不要** | **接続可（参考値）** |
| 保護区域の公式指定 | **Protected Planet / WDPA**（`api.protectedplanet.net`） | REST/JSON | **トークン必要**（無償・申請フォーム） | 任意接続（後述） |
| 物理的な水リスク | **国土地理院 ハザードマップポータル タイル**（`disaportaldata.gsi.go.jp/raster/<layer>/{z}/{x}/{y}.png`） | XYZラスタタイル。洪水浸水想定（想定最大規模）・高潮・津波・土砂災害警戒区域（急傾斜地/土石流/地すべり） | **不要** | **接続可** |
| 生態系サービス | 単一の権威データセットは**存在しない** | — | — | **代理指標のみ**（後述） |

### 結論

- **生物多様性上重要な地域** → GBIF ＋ OSM保護区域で **判定可能にする**
- **物理的な水リスク** → 国土地理院ハザードタイルで **判定可能にする**
- **生態系サービス** → 権威データが無いため、**代理指標（proxy）**として提示し、「判定済」とは表示しない

これにより 5基準中 **2 → 4 が判定可能**、残り1は代理指標付きとなる。

## 2. 技術的な制約と、それに対する設計

### Cloudflare Workers 無料枠：CPU 10ms／サブリクエスト 50件

**ラスタタイルのピクセル復号はできない。** PNGを1ピクセル読むにも全IDATの展開とフィルタ解除が要り、10msに収まらない。

→ **タイルの存在有無で判定する。** 国土地理院のタイル配信は、該当データが無い区画では 404 を返す。
つまり `200` は「そのタイル範囲内に該当区域が存在する」、`404` は「存在しない」を意味する。
復号は一切不要で、HTTPステータスのみで判定できる。

**この方式の限界を仕様として明示する：** z16 のタイルは一辺約 600m（緯度35度）。
したがって判定結果は「**この地点の周辺約600m四方に該当区域が存在する**」であり、
「この地点そのものが該当区域内にある」ではない。
スクリーニング用途としては妥当だが、帳票にこの旨を必ず併記する。

### サブリクエスト数

1地点あたり：GBIF 2 ＋ Overpass 1 ＋ ハザードタイル 6 = **9件**。
複数地点は逐次処理し、D1にキャッシュする（同一地点の再取得を避ける）。

### 外部APIの不確実性

Overpass は混雑時に遅く、レート制限もある。GBIFは安定だがレスポンス形状の変更はあり得る。
→ **1つの取得失敗が帳票全体を壊さない設計にする。** 各データ源は独立して成功／失敗し、
失敗した源は「取得失敗」と表示する。**無言で省略しない。**

### 検証できないことの明示

サンドボックスから外部APIへ到達できないため、**私はレスポンス実物を確認できない**。
そこで既存の定時セルフチェック（`system_checks`）に新データ源を追加し、
デプロイ後に本番から実際に取得できたかを記録する。**これが検証手段になる。**

## 3. 実装

### 3.1 新規モジュール `worker/src/lib/publicData.ts`

- `fetchBiodiversity(lat, lng)` — GBIF。半径3km。総記録数、種数、IUCN絶滅危惧カテゴリ（CR/EN/VU）別件数
- `fetchProtectedAreas(lat, lng)` — Overpass。半径10km。最寄りの保護区域の名称・種別・距離
- `fetchHazards(lat, lng)` — 国土地理院タイル6種。z16でHTTPステータス判定
- `fetchEcosystemServiceProxy(...)` — 上記＋自前の植生指標から代理指標を組み立て

すべて D1 `public_data_cache` にキャッシュ（source × 丸め座標 × 取得日）。

### 3.2 マイグレーション

`public_data_cache`（source, lat, lng, payload_json, status, fetched_at）

### 3.3 LEAP帳票への反映

`sensitive` 5基準を新データで再構成。各基準に**データ源と取得日時**を併記。

### 3.4 UI／UX

企業担当者の仕事は「自社拠点が何かに近接していないかを、**出典付きで**確認すること」。

- **導線** — 判断する場所に置く。スクリーニング報告の第3章に、未取得なら照合を促すカードを出す
- **実行** — 「公的データと照合」ボタン1つ。データ源ごとに進捗を段階表示（既存の AgentSteps を再利用）
- **結果** — 生データではなく**距離と該当有無のチェックリスト**として提示
  例：「保護区域：最寄り 2.3km（○○国定公園）」「洪水浸水想定：該当あり（想定最大規模）」
- **出典の隣接** — 数値のすぐ隣に必ずデータ源と取得日。商談で「それは何のデータですか」に即答できる状態にする
- **失敗の可視化** — 各源に 取得成功／取得失敗／未接続 のチップ。失敗を隠さない
- **留保の併記** — OSMは市民参加型データなので「参考値。正式な指定は所管行政庁で確認」を必ず添える

## 5. 接続しないもの（およびその理由）

- **Protected Planet / WDPA** — 無償だがトークン申請が必要。設定画面からトークンを登録した場合のみ有効化する任意接続とする。未登録でもOSMで代替できるため、必須にはしない。
- **生態系サービスの権威データ** — 存在しない。保安林等の法的指定は全国規模のオープンAPIとして提供されていない。代理指標にとどめ、「判定済」とは表示しない。

## 6. 実装結果（本番検証）

### 6.1 接続できたもの

| データ源 | 状態 | 本番セルフチェック実測 |
|---|---|---|
| GBIF Occurrence API | **接続** | `ok (87,678件)` — 東京駅半径3kmで実データ取得、所要 125–192ms |
| 国土地理院 ハザードマップタイル | **接続** | `ok（判別可: 該当地=200/3977B、非該当地=404）` — 所要 1.1–2.3秒 |
| OpenStreetMap（Overpass） | **接続可・恒常的に混雑** | 3ミラーとも `521 / 429 / 429`。下記6.3 |

### 6.2 「判別できるか」を検証した理由

水リスク判定は、タイル配信が「該当地で200・非該当地で404」を返すことに全面的に依存する。
正例（東京都心＝荒川洪水浸水想定区域内）だけを確認した状態では、**どこでも200を返すサービス**でも
チェックは緑になり、その結果すべての拠点が「該当あり」と印字される。企業へ渡す文書でこれは起こしてはならない。

そのため負例（富士山頂＝浸水想定の指定なし）を追加し、**両者を区別できなければチェックを失敗させる**。
本番実測は `該当地=200/3977B、非該当地=404` で、判別できることを確認済み。

### 6.3 Overpass が繋がらない件（設計上の判断）

Overpass の各インスタンスは**送信元IP単位**でレート制限をかける。Cloudflare Workers は
プラットフォーム全体で共有の送信元IPから外へ出るため、429 は「このシステムの不具合」ではなく
**構造的に発生する通常状態**である。3ミラーへのフォールバックを入れてなお解消しない。

そこで「失敗」と「混雑」を区別した。

- 429 または 5xx（＝提供側の事情）→ **混雑**。帳票では琥珀色の「提供元が混雑」チップ、
  文書出力では「提供元が混雑のため未取得」。任意項目である旨も併記する
- それ以外の 4xx、DNS・パースエラー（＝こちら側の事情）→ **取得失敗**。従来どおり赤で表示

同じ判定関数 `isProviderSideStatus` をライブ取得と定時セルフチェックの両方で使う。
別々の条件で書くと必ず食い違うため。定時チェックも、全ミラーが提供側事情で応答不可の場合は
赤にしない — 毎日赤い行が出る管理画面は、担当者が読まなくなる。

なお、保護区域が取得できなくても「生物多様性にとって重要な地域」の判定はGBIF単独で成立する。
保護区域は判定を**補強する**任意項目であり、依存項目ではない。

### 6.4 感度の高い地域 5基準の最終状態

| 基準 | 状態 | 根拠 |
|---|---|---|
| 生物多様性にとって重要な地域 | **判定済** | GBIF（IUCNカテゴリ別ファセット）＋ OSM保護区域（取得できた場合） |
| 生態系の完全性が高い地域 | **判定済** | 自システム10mメッシュ解析 |
| 生態系の完全性が急速に低下している地域 | **判定済** | 自システム10mメッシュ解析（前年比） |
| 物理的な水リスクが高い地域 | **判定済** | 国土地理院ハザードマップタイル（洪水・高潮・津波） |
| 生態系サービス供給上、重要な地域 | **代理指標** | 全国規模の権威データが存在しないため。「判定済」とは表示しない |
